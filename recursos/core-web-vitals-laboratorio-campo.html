Cómo medir Core Web Vitals sin confundir laboratorio y usuarios reales

Una prueba de velocidad puede mejorar hoy y el reporte de usuarios reales seguir mostrando problemas. Las mediciones responden preguntas distintas. Para priorizar cambios conviene saber qué se midió, en qué condiciones y a qué página o conjunto de páginas corresponde el resultado.

Identifica las tres métricas y su referencia

La documentación de Core Web Vitals de Google identifica tres métricas: LCP para carga del contenido principal, INP para respuesta a las interacciones y CLS para estabilidad visual. Sus umbrales de experiencia buena son LCP de hasta 2,5 segundos, INP de hasta 200 milisegundos y CLS de hasta 0,1.

Google plantea evaluar el percentil 75, separando móvil y escritorio. Ese valor no es el promedio: ayuda a observar una parte menos favorable de la distribución. Al registrar un resultado, conserva métrica, dispositivo y origen de datos, además del número.

La puntuación general de rendimiento de una prueba no sustituye estas métricas ni resume toda la experiencia de un sitio.

Usa laboratorio para investigar y campo para observar

Google distingue en su guía de medición datos de campo obtenidos de usuarios reales y datos de laboratorio recogidos en un entorno controlado. El laboratorio permite estudiar una versión antes de publicarla. El campo refleja dispositivos, redes y recorridos que la prueba aislada puede no reproducir.

Una carga estándar de Lighthouse sin interacción no mide INP. TBT puede servir como señal de diagnóstico, pero no debe reportarse como si fuera INP. Herramientas interactivas de desarrollo permiten investigar respuestas concretas; una sesión local tampoco equivale a una distribución de usuarios reales.

Como criterio de revisión, utiliza ambos tipos de evidencia y conserva sus etiquetas. Si discrepan, investiga las condiciones de cada medición antes de descartar una.

Revisa si PageSpeed informa sobre la URL o el sitio

Según la documentación de PageSpeed Insights, sus datos de campo provienen de CrUX y abarcan los 28 días anteriores. Cuando una URL no tiene muestras suficientes, puede mostrar datos del origen, que agrupan experiencias del sitio. Si tampoco hay datos suficientes del origen, no se muestra esa experiencia de campo.

Por eso, anota si estás viendo “esta URL” o el origen. La falta de datos de campo no confirma que una página sea rápida. Tampoco atribuyas automáticamente al artículo nuevo el resultado agregado de otras páginas.

La documentación contempla una evaluación con LCP y CLS cuando falta información suficiente de INP. Revisa qué métricas sostienen el estado mostrado en vez de asumir que siempre existen datos completos de las tres.

Un procedimiento de medición que puedas repetir

  1. Escoge el recorrido: página de entrada, contenido y contacto, según lo que realmente hace el visitante.
  2. Guarda una línea de base: URL exacta, fecha, versión publicada, dispositivo, condiciones y reporte.
  3. Observa el problema: identifica qué elemento carga tarde, qué interacción responde lento o qué contenido se desplaza.
  4. Propón un cambio verificable: por ejemplo, revisar una imagen principal o un script concreto, en vez de modificar todo a la vez.
  5. Repite la prueba: usa condiciones comparables y comprueba que la mejora no rompió funciones.
  6. Revisa la evolución en campo: considera la ventana de datos antes de atribuir el resultado al despliegue.

Esta es una propuesta editorial de trabajo. Sirve para documentar decisiones y evitar que una captura aislada se convierta en toda la evaluación técnica.

Ejemplo hipotético y límites de la conclusión

Una landing cambia su imagen inicial y el laboratorio muestra mejor carga en condiciones comparables. El reporte de campo todavía incluye visitas de días anteriores al cambio. La conclusión prudente es que la prueba controlada mejoró y que falta observar cómo evoluciona la experiencia real.

Si el formulario sigue saltando al cargar un aviso, o el botón tarda en responder, continúa la investigación del recorrido completo. Elegir solo el resultado favorable deja problemas de uso sin atender.

Prioriza cambios con evidencia y revisa funcionalidades, accesibilidad y contenido en paralelo. Core Web Vitals permite evaluar aspectos del rendimiento; aprobar sus umbrales no garantiza posiciones en buscadores, conversiones ni que todas las personas tengan la misma experiencia.
