Salidas estructuradas de IA: cómo validar los datos antes de usarlos

Un agente puede entregar todos los campos esperados y aun así proponer una referencia inexistente o una cantidad equivocada. Las salidas estructuradas facilitan la integración, pero el sistema necesita decidir qué valores puede aceptar. Esta guía organiza esa validación entre la respuesta del modelo y el registro definitivo.

Qué resuelve el esquema

Un esquema describe la forma de la respuesta: campos, tipos y opciones permitidas. Por ejemplo, una solicitud puede incluir referencia, unidades y observaciones. La documentación de OpenAI diferencia el JSON válido de la adhesión al esquema y advierte que una salida estructurada todavía puede contener errores. También contempla rechazos y entradas que no corresponden a la tarea.

Define qué significa un campo vacío. Una referencia desconocida debe poder quedar pendiente, en lugar de obligar al modelo a elegir una opción para cumplir el formato. El equipo técnico debe revisar qué partes del esquema admite la interfaz y el modelo que realmente utiliza.

Organiza tres controles antes de guardar

  1. Formato: comprueba que la respuesta terminó correctamente y que se puede interpretar según el esquema esperado.
  2. Datos: consulta si la referencia existe, si la cantidad usa la unidad correcta y si la fecha es posible para ese proceso.
  3. Acción: verifica que el usuario y el agente pueden realizar la operación sobre ese registro concreto.

Conviene devolver errores específicos. “Referencia no encontrada” permite corregir el dato; “falló la IA” deja al asesor sin una siguiente acción. Conserva el identificador de la solicitud para que una corrección no cree un segundo registro independiente.

Ejemplo hipotético: una solicitud de repuestos

Un cliente ficticio pide dos cajas de una pieza. El modelo devuelve dos unidades con una referencia válida. El formato pasa, pero la unidad comercial no coincide. El sistema consulta el catálogo, muestra que cada caja contiene varias unidades y pide confirmar la presentación antes de reservar existencias.

Otra solicitud trae una referencia retirada. No conviene sustituirla automáticamente por la más parecida. La salida puede proponer una revisión y presentar alternativas verificadas, dejando explícito que el cliente todavía no eligió una. Estos escenarios son pruebas de diseño, no resultados de clientes de Nicho.

Define el tratamiento de respuestas incompletas

Una respuesta interrumpida, un rechazo del modelo y un dato que incumple una regla de negocio necesitan caminos diferentes. En el primer caso puede corresponder reintentar de forma limitada; en el segundo, ofrecer una ruta permitida; en el tercero, solicitar una corrección concreta. No reintentes indefinidamente la misma entrada esperando que aparezca un valor aceptable.

Antes del lanzamiento, prueba cantidades negativas, monedas ausentes, referencias similares, campos vacíos y respuestas fuera de alcance. El criterio de aceptación debe indicar qué se guarda, qué se consulta y qué queda detenido en cada caso. Cuenta los errores evitados y las revisiones necesarias, sin convertir una tasa de formato correcto en una promesa de exactitud comercial.

Cómo encaja con tu operación

Si los datos proceden de archivos, revisa también la guía para extraer y comprobar datos de documentos. Para operaciones que cambian información, define los permisos del agente en el CRM. Cada control debe tener un responsable y una respuesta comprensible para el asesor.
