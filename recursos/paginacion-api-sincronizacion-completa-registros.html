Cómo comprobar que una integración leyó todos los registros de una API

Una API puede responder correctamente y entregar solo una parte de los registros. Si la integración interpreta esa respuesta como una lista completa, el tablero mostrará menos información sin un error evidente. La paginación necesita una condición de finalización y una forma segura de retomar el recorrido.

Identifica cómo continúa la API

Algunas interfaces entregan un enlace a la página siguiente; otras usan un cursor o un número de página. Microsoft Graph documenta la paginación mediante enlaces de continuación y recomienda utilizar el enlace devuelto para recuperar las páginas restantes.

No construyas el siguiente enlace suponiendo cómo se forma un token opaco. Mantén filtros y alcance coherentes durante el recorrido. Una respuesta vacía tampoco debería interpretarse como final sin comprobar el contrato de esa API: puede existir una continuación aunque la página actual no aporte elementos útiles al filtro local.

Guarda progreso después de confirmar el procesamiento

Separa obtener una página, validar sus registros, escribir el resultado y guardar el punto de continuación. Si avanzas el cursor antes de confirmar el procesamiento, una interrupción puede dejar registros atrás. Si repites una página al recuperar, necesitas reconocer los registros ya aplicados.

Registra hora de inicio, alcance, páginas procesadas, fallos y condición final. El contador de elementos ayuda a investigar, pero no sustituye la señal de finalización de la API. No compares dos recuentos tomados en momentos distintos como si fueran una foto estable de datos que siguen cambiando.

Ejemplo hipotético: sincronizar un catálogo

Una tienda ficticia recibe el catálogo en varias páginas. Después de la segunda, el proceso se interrumpe. Al volver, retoma desde el último punto confirmado o reprocesa de forma segura la página pendiente, según el diseño. El estado permanece “sincronización parcial” hasta completar el recorrido.

Si el sistema destino elimina productos que no vio en la lista, una lectura parcial sería especialmente peligrosa. La eliminación por ausencia debe esperar una comparación completa y válida, con protección frente a cambios concurrentes y reglas de negocio verificadas. Ante un fallo, conserva el inventario anterior y marca la revisión pendiente.

Diseña pruebas que superen una sola página

  • Usa suficientes registros sintéticos para recorrer varias páginas.
  • Interrumpe después de leer y antes de guardar una página.
  • Simula una respuesta repetida y un límite temporal del proveedor.
  • Incluye un registro que cambia mientras el recorrido sigue abierto.
  • Comprueba qué ocurre si el cursor vence o deja de ser válido.

La recuperación puede necesitar reiniciar una lectura completa o usar un mecanismo incremental específico. Define ese procedimiento antes de poner la integración en producción. El panel debe mostrar hasta cuándo están conciliados los datos, de modo que el equipo conozca la antigüedad de la información que consulta.
