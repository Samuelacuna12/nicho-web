Software y continuidad operativa

Cómo definir qué puede hacer tu software cuando se pierde la conexión

Un vendedor en ruta puede seguir tomando información aunque pierda señal. Eso no significa que el pedido ya exista en el sistema central ni que el inventario esté reservado. Antes de contratar un modo sin conexión, define qué trabajo puede continuar y qué decisiones deben esperar una confirmación.

1. Separa consultar, preparar y confirmar

Haz una lista de acciones y clasifícalas. Consultar un catálogo descargado puede ser útil si muestra cuándo se actualizó. Preparar una solicitud puede permitirse sin red. Confirmar existencias, aceptar un pago o comprometer una fecha de entrega necesita una regla adicional: no debería presentarse como hecho solo porque el formulario se guardó en el equipo.

Para cada acción, registra el dato necesario, su antigüedad tolerable, quién puede ejecutarla y qué respuesta verá la persona. Define también una alternativa cuando el dato esté vencido: capturar interés, dejar pendiente o contactar al responsable por un canal disponible. No prometas que toda la aplicación funcionará desconectada.

2. Diseña estados que no confundan guardado con recibido

Propón estados visibles: borrador local, pendiente de envío, enviado sin confirmación, confirmado y requiere revisión. Un identificador local permite reconocer la operación, pero no equivale al número definitivo del pedido. Muestra ambos cuando corresponda y conserva la relación entre ellos.

MDN advierte que navigator.onLine no demuestra acceso efectivo a Internet: un dispositivo puede estar conectado a una red local sin alcanzar el servicio. Úsalo como orientación, no como comprobante de entrega. La confirmación debe depender de la respuesta verificable del sistema que recibe la operación.

Si desaparece la conexión después de enviar, el resultado puede ser incierto. Antes de reenviar, consulta el estado de esa misma operación cuando sea posible; no la conviertas automáticamente en una solicitud nueva.

3. Acuerda cómo resolver los cambios al reconectar

El catálogo pudo cambiar mientras el vendedor estaba fuera de línea. Compara la versión utilizada con las reglas actuales y muestra diferencias relevantes: precio, disponibilidad, responsable o condición comercial. No reemplaces silenciosamente lo que el cliente vio ni aceptes sin revisión una condición vencida.

Para una solicitud nueva, el servidor puede aceptarla o devolver motivos concretos para corregirla. Para una edición, evita borrar cambios hechos por otra persona: aplica controles de versión y resolución de conflictos. Define quién decide y cuánto tiempo puede permanecer un caso en revisión.

También necesitas un identificador estable para que un reintento no cree otra operación. El principio de idempotencia complementa la sincronización, pero no resuelve por sí solo una diferencia de precios.

4. Limita los datos que quedan en el dispositivo

Define qué información se guarda, durante cuánto tiempo y qué ocurre al cerrar sesión, cambiar de usuario o perder el equipo. No descargues toda la cartera comercial para una tarea que solo necesita referencias de producto. El almacenamiento local no debe presentarse como una copia de seguridad garantizada.

La implementación debe contemplar equipos compartidos y borrado de datos del navegador. Si hay pendientes, comunica el riesgo antes de una acción que pueda eliminarlos y ofrece una recuperación aprobada. No recomiendes exportar información privada a archivos personales como solución improvisada.

5. Ejemplo ficticio y prueba de aceptación

Una distribuidora ficticia prepara tres solicitudes durante una visita sin señal. Al reconectar, dos quedan confirmadas y una requiere revisión porque cambió el precio. Son cantidades inventadas para explicar el flujo, no resultados de un cliente de Nicho. El resumen muestra dos confirmaciones y un pendiente, nunca “tres pedidos completados”.

  • Corta la conexión antes del envío y después de que el servidor reciba la solicitud.
  • Reconecta dos veces y comprueba que no aparezcan duplicados.
  • Cambia un precio mientras el equipo está desconectado.
  • Cierra y vuelve a abrir la aplicación con pendientes.
  • Prueba con otro usuario y verifica que no vea información ajena.
  • Revisa que cada pendiente tenga motivo, responsable y siguiente acción.

Entrega este recorrido como parte de las pruebas de aceptación del software. La meta es conservar trabajo y comunicar sus límites, no esconder la falta de conexión detrás de un indicador verde.
