Cómo definir el alcance de un MVP de software

Para pedir un sistema conviene llevar algo más preciso que una lista de pantallas. El punto de partida es un trabajo que alguien necesita terminar: aprobar una compra, recibir un pedido o cerrar una solicitud. Un MVP puede cubrir un recorrido pequeño y completo, con reglas claras para saber si quedó bien.

Empieza por una operación que puedas observar

Escoge un proceso con inicio y final reconocibles. Entrevista a quien lo ejecuta y revisa un ejemplo reciente, ocultando los datos personales que no sean necesarios. Anota qué llega, quién decide, qué información consulta y qué entrega a la siguiente persona. Incluye el paso que hoy ocurre por fuera de la hoja de cálculo o del correo.

Como propuesta de trabajo, escribe una ficha con estos campos: disparador, responsable, entradas, decisiones, resultado y excepciones. Para una solicitud de compra, el inicio podría ser el envío de la solicitud y el final su aprobación o rechazo. La recepción de mercancía puede pertenecer a otro recorrido.

Recorta el alcance sin dejar el proceso a medias

Separa las capacidades en tres grupos: necesarias para completar ese recorrido, útiles para una siguiente versión y pendientes de investigación. Una función desconocida merece una pregunta o una prueba técnica; incluirla como si estuviera resuelta hace frágil la estimación.

  • Primera versión: registrar una solicitud, asignarla, decidir y consultar su historial.
  • Después: recomendaciones de compra, comparaciones avanzadas o reportes adicionales.
  • Por verificar: acceso al sistema contable, permisos de su API y datos disponibles.

El alcance debe decir también qué ocurre si una persona se ausenta o falta información. Esas situaciones pueden definir si el proceso se puede usar desde el primer día.

Convierte cada regla en una comprobación

La guía de Azure Boards de Microsoft propone definir los criterios de aceptación antes de comenzar y usarlos como base de las pruebas. Para aplicarlo, cambia frases como “el módulo será fácil de usar” por condiciones observables.

Ejemplo hipotético: una empresa quiere aprobar solicitudes de insumos. Los siguientes criterios son ilustrativos y deben ajustarse con sus responsables:

  1. Una solicitud sin centro de costo no se envía y muestra qué falta, conservando los datos ya escritos.
  2. Solo el aprobador asignado o su reemplazo autorizado puede aprobarla.
  3. Al rechazarla se exige un motivo que el solicitante puede consultar.
  4. Un doble clic en “Enviar” no crea dos solicitudes.
  5. El historial conserva autor, fecha, estado anterior y estado nuevo.

Define con qué usuario y con qué datos se probará cada condición. El equipo que construye y la persona que recibe deberían entender lo mismo al leerla.

Incluye datos, permisos y operación

Una pantalla terminada puede depender de tareas que todavía nadie presupuestó. Documenta qué registros se migran, qué campos se necesitan, quién puede exportar información y cómo se recupera el sistema si falla. Pide que el alcance incluya el ambiente de pruebas, la entrega de accesos y una explicación de las tareas de administración.

También conviene acordar quién responde preguntas de negocio y quién valida la entrega. Si dos áreas usan la palabra “aprobado” con sentidos distintos, resuélvelo antes de desarrollar. Guarda esas decisiones junto al alcance para evitar que una conversación posterior cambie silenciosamente lo acordado.

Si el alcance incluye información que hoy vive en archivos, prepara la migración de hojas de cálculo sin perder el origen de los datos.

Decide si el MVP está listo para construirse

Recomendamos iniciar cuando el recorrido principal puede explicarse de principio a fin, las excepciones importantes tienen salida y los criterios permiten aceptar o rechazar una entrega con evidencia. Si todavía no se sabe quién aprueba o qué datos son confiables, una etapa de definición puede ser más útil que comenzar a programar.

El documento no elimina cambios. Establece una base para discutirlos: qué necesidad nueva aparece, qué parte afecta y qué se aplaza o amplía. Tampoco confirma que una integración sea viable; esa decisión necesita revisar las capacidades, permisos y condiciones del proveedor correspondiente.
